Before the next input event a retrying assertion is not a wait at all — it resolves at first-true, sooner than the sleep it replaced — so that gap needs a bound the application emits: an acknowledgement it publishes beats a count of scheduler steps, admissible only where the test cites the app source scheduling them, which beats a duration. Before a read the assertion IS the wait. Where the application emits no readiness signal at all, that absence is the finding.
_Avoid_: `press(key); await expect(x).toHaveCount(n); press(key)` — an assertion as the only gap between two inputs; `waitForTimeout(300)`, `Bun.sleep(20)`, `cy.wait(500)` after a click, a keypress, or a boot; a scheduler-step count citing no app source that schedules it.
Detect: anchor on pairs of inputs, never on waits — the defect is usually the absence of one, so a scan keyed to `waitForTimeout(` cannot see its own worst case. An input is anything the test dispatches to the app — click, press, type, fill, hover, goto, drag, or a message sent over a socket — including one wrapped in an assertion (`expect(await clickBold(page)).toBe(true)`). Two inputs with at least one assertion and nothing else between them is the finding; resolve helpers first, since one ending in a settle orders the pair. Then two lexical scans: a blocking sleep after an input (`waitForTimeout`, `Bun.sleep`, `cy.wait`, `setTimeout` in a promise — never a poll interval or timeout budget, which parameterise a wait some condition already bounds), and a fixed scheduler-step count whose comment cites no app source scheduling those steps.
Not-when: a timer the app owns IS the subject of the assertion and the test cites that timer's constant instead of retyping its value; or the duration bounds an assertion that something did NOT happen, which is an observation window with no signal to wait for.
