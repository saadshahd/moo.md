A comment earns its place by naming something the code cannot say. Where a line needs explaining, reach first for a rename, an extraction, or a restructure; write the comment when none of those carry the point. Block comments belong where the code cannot be made self-describing, and they explain WHY, never WHAT. A `//` comment survives only when omitting it would let a future editor silently break a non-obvious constraint, so it MUST name a consequence or an external-system mapping. A comment that narrates the edit rather than the code — "updated to fix X", "now also handles Y", "changed from Z" — is always wrong: change history belongs in the commit message, not the source. A comment that defends code against change — `IMPORTANT`, `do not remove`, `talk to X first` — earns its place only once its claim is traced to a path live today; then encode the constraint as a type, a runtime check, a test or a lint rule, which fails loud, and delete the comment, keeping it only where none of those can carry the constraint.
_Avoid_: a comment that restates the code beneath it in English; a WHAT-narration of a loop, assignment, or call; step-by-step narration of a function body; a comment narrating the edit's history ("updated", "was", "now", "previously") instead of the code's present behavior; a `do not remove`, `too risky` or `fine for now` comment kept on its word.
Detect: read each comment against its line — if the line's identifiers already say what the comment says, delete it. The one sanctioned inline exception is a comment stating a type or shape the code cannot express on its own, documenting SHAPE only — never behavior. For a comment guarding against change, trace its claim to a caller, path or test that still exercises it; none found → the claim is stale, delete the comment; found → look for the type, check, test or lint rule that could carry it.
Not-when: the comment encodes a genuine external constraint (regulation, a documented upstream bug, a measured performance tradeoff) that the code cannot express on its own — keep it, and make it name the WHY; or the comment is a doc-comment on a published module's exported surface, read through hover or generated docs by consumers who never open the body — there a one-line intent summary, plus error semantics the signature cannot name, earns its place, while boilerplate restating the signature does not.
