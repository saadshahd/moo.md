A single commit holds one kind of change — a restructure with no behavior change, a behavior change with no cleanup riding along, or an edit to an agent instruction (a skill, a prompt, a CLAUDE.md) — never two, because a failing check after a mixed commit can't tell you which change broke it. The same reason orders a series: the tidy lands first, deleting dead code, redundant validators and stubs before the addition they clear room for; and a sweep of similar edits, even tool-applied, runs the check after each unit and advances only when it passes, so a failure points at one unit.
_Avoid_: a commit message with both a refactor verb ("extract", "rename", "inline") and a behavior verb ("fix", "add", "change"); a skill or prompt fix riding inside the feature commit that exposed it — note it, keep the task moving, land it alone; a deletion of dead code landing after the feature it made room for.
Detect: per-commit diff — do the touched lines include both a rename/move (detectable via git's move-detection or near-identical line matches elsewhere in the diff) and a line whose logic/branching actually differs, not just relocates; a commit touching both an agent-instruction file and source; in a series, a deletion commit after the addition it clears, or a sweep landed whole and then a fix-up commit.
Not-when: the tidy is a genuinely mechanical, tool-applied rename (e.g. an IDE rename-symbol across a whole repo) landing in its own commit anyway — still separate, just cheap to separate.
